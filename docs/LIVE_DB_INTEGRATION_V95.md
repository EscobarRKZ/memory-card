# Memory Card v95 — rollback-only production-schema authorization integration

**Дата:** 9 ноября 2026. **Проверяемый проект:** `nzcbapjgwqqafmacizqe` (Memory Card, Supabase Free). **Версия опубликованной PWA:** v94 — интерфейс/Service Worker не менялись в этом этапе.

## Зачем нужен этот тест

До v95 критичные сценарии проверялись преимущественно имитациями RPC и статическими условиями SQL. В этой итерации серверная безопасность испытана против **реальных PostgreSQL функций и RLS-политик действующего проекта**, но с временными фикстурами, которые удаляются откатом транзакции.

Тесты записаны в двух файлах:
- [`tests/live_cloud_cas_v95.sql`](../tests/live_cloud_cas_v95.sql) — права на игры/профили/настройки и сравнение версий.
- [`tests/live_social_authorization_v95.sql`](../tests/live_social_authorization_v95.sql) — друзья, списки, блокировки и ограничения доступа.

## Методика и безопасность

Каждый тест начинается с `BEGIN` и заканчивается явным `ROLLBACK`. Транзакция создаёт ровно две фиктивные записи `auth.users` на `@example.invalid`, а реальные триггеры создают связанные профили и настройки. Внутри транзакции `SET LOCAL ROLE authenticated` ограничивает SQL до прав, которыми обладает пользователь веб-приложения, а `set_config('request.jwt.claim.sub',<test UUID>,true)` имитирует каждого из двух авторизованных пользователей.

Это **не** создаёт реальных сессий Supabase Auth, не отправляет email и не требует пароля или доступа к настоящим двум пользователям. Разные подставленные UID действуют последовательно в **одном соединении**. Запросы не отправляются из телефона или браузера.

Если SQL-assertion падает, стандартная транзакция завершается с ошибкой и не должна фиксировать изменения. После каждого запуска обязательно перепроверяются итоговые счётчики. В CI включена только **статическая защита файлов сценариев** — SQL не исполняется автоматически против рабочего Supabase.

## Успешные фактические проверки

### Облачные игры и настройки
- RLS не показывает под UID A игры B, его профиль или настройки; зеркальная проверка B против A тоже пройдена.
- Прямое изменение/вставка игры другого аккаунта отклоняется.
- Серверный `save_games_if_unchanged` принимает актуальную ревизию собственной игры, возвращает новую версию и отклоняет stale revision.
- Даже если B знает точную обновлённую ревизию игры A, CAS-обновление от B не может изменить её.
- При вставке `user_id` из тела API не определяет владельца: сервер принудительно использует `auth.uid()`.

### Друзья и приватность
- До принятия приглашения чтение чужой игровой библиотеки недоступно.
- Отправитель не может сам принять собственное приглашение; получатель принимает ровно один раз.
- Принятому другу доступны разрешённые игры и статистика, но не личные заметки и не Backlog.
- Блокировка скрывает принятую дружбу и запрещает профиль/встречные приглашения.
- Разблокировка не возобновляет дружбу самостоятельно. Новое приглашение и его принятие работают штатно.
- Гость не имеет `EXECUTE` для проверенных привилегированных social RPC; клиентская роль не имеет прямого изменения `friendships`.

## Проверка сохранности реальных данных

После каждого полного теста, в ответе из SQL за границей `ROLLBACK`, возвращалось:
- `remaining_users: 2`
- `remaining_games: 110`
- `remaining_fixture_users: 0`

После социальной проверки также:
- `remaining_friendships: 0`
- `remaining_blocks: 0`
- `remaining_request_audit_rows: 0`

Эти результаты подтверждают, что проверочные строки не сохранились. Они не заменяют независимый внешний аудит репликации, журналов или восстановления из резервных копий.

## Что ещё не протестировано

Это **сильнее моков**, но не равно полноценной проверке пользовательской регистрации: нет настоящих email-писем/токенов Auth, двух одновременных подключений, гонки `accept`/ `block` с реальным contention, теста логина/выхода и удаления двух одноразовых Auth аккаунтов через Edge Function, испытаний Android/iOS и лимитов нагрузки. Эти требования остаются обязательными перед Google Play.

**Безопасность повторного запуска:** запускать файлы только целиком; не выделять вручную отдельные `INSERT`/ `UPDATE` из них. При переносе в отдельную тестовую организацию проверить схему и не использовать реальные user IDs. Не помещать какие-либо production credentials в репозиторий.
